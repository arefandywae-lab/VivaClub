# 🎯 Technical Solution & Architecture Justification (VivaClub)

เอกสารสรุปประกอบการนำเสนอ (Presentation) เพื่อใช้อธิบายแนวคิดเชิงวิศวกรรม (Engineering Decisions) โครงสร้างสถาปัตยกรรม ข้อจำกัด และเหตุผลในการเลือกใช้เทคโนโลยีต่างๆ ในโปรเจกต์ VivaClub

## 1. External & Gateway (หน้าด่านและการรักษาความปลอดภัย)

ส่วนนี้คือปราการด่านแรกที่รับ Traffic จากโลกภายนอก (Public Internet)

*   **Caddy Server (Reverse Proxy)**
    *   **ทำไมถึงใช้ / ดีกว่าตัวอื่นยังไง:** เราเลือกใช้ Caddy แทนที่จะใช้ Nginx สุดฮิต เพราะ Caddy มีจุดเด่นเรื่อง **"Automatic HTTPS"** มันสามารถไปขอและต่ออายุ Certificate จาก Let's Encrypt ให้เราเองแบบฝังในตัวโดยไม่ต้องลง Certbot เพิ่มเหมือน Nginx นอกจากนี้ Caddyfile (ไฟล์คอนฟิก) อ่านง่ายและสั้นกว่า Nginx มาก ทำให้ลด Human Error ตอน Deploy บน VPS ได้มหาศาล
    *   **ตัวอย่างการใช้งาน:** เมื่อมีคนเรียก API `https://api.vivaclub.com/api/users` Caddy จะทำหน้าที่เป็นกันชน ตรวจสอบ SSL และซ่อน IP จริงของคอนเทนเนอร์ Django เอาไว้เบื้องหลัง (Security by Obscurity)
    *   **ข้อจำกัด:** Ecosystem หรือ Plugin เสริมอาจจะไม่เยอะและเก่าแก่เท่า Nginx หากต้องทำ Load Balancing แบบซับซ้อนมากๆ Nginx/HAProxy อาจจะยืดหยุ่นกว่า
*   **Clients (แอปพลิเคชันฝั่งผู้ใช้)**
    *   **Flutter (Mobile App):** เลือกใช้เพราะทำ Cross-platform (iOS/Android) ได้จาก Codebase เดียว มีไลบรารีสตรีมมิ่งเสียงที่เสถียร 
    *   **Next.js (Admin Dashboard):** แยก Subdomain ออกมาเพื่อจัดการระบบหลังบ้าน ไม่กวน Traffic ของแอปมือถือ

## 2. Internal VPS: Backend Layer (หัวใจการประมวลผล)

เราใช้สถาปัตยกรรมแบบ Hybrid Backend ภายในวง Network (Docker Compose) ของตัวเอง:

*   **ทำไมถึงเช่า VPS (Virtual Private Server) แทนที่จะปาขึ้น Cloud PaaS สำเร็จรูปอย่าง Railway / Heroku / Vercel?**
    *   **ปัญหาเรื่อง Port ของ WebRTC:** บริการอย่าง Railway หรือ Heroku ส่วนใหญ่จะเปิดทางให้เฉพาะเว็บพอร์ตมาตรฐาน (80/443 TCP) แต่แอปเราต้องใช้ **Port 7882 แบบ UDP** มหาศาลเพื่อสตรีมเสียง ถ้าไปใช้ PaaS พวกนี้ เราจะถูกบล็อกไม่ให้ใช้ UDP เลย ทำให้ระบบเสียงพังสนิท
    *   **Control & Networking:** บริการ PaaS จะรันแต่ละโปรแกรมแยกส่วนกันชัดเจน การจะให้ Redis คุยกับ Django แล้วให้ Bot Worker วิ่งไปต่อ LiveKit ในวงปิด (Private Network) ทำได้ยากและตั้งค่าซับซ้อน พอเราเช่า VPS เปล่าๆ (เช่น DigitalOcean, AWS EC2) แล้วครอบด้วย Docker Compose เราเหมือนมี "โลกส่วนตัว" ที่ทุก Container คุยกันเองได้เต็มความเร็ว (Localhost speed) และเราควบคุมได้ 100% ว่าจะเปิดพอร์ตไหนให้โลกภายนอกเห็น
    *   **ความคุ้มค่า (Pricing):** โพรเซสอย่าง Music Bot ต้องรันข้ามวันข้ามคืน (Long-running Tasks) ถ้าไปขึ้น Railway จะถูกคิดเงินตามหน่วยความจำและเวลาเป็นรายนาที ซึ่งบานปลายมาก การเหมา VPS เป็นรายเดือนจึงประหยัดและกะเกณฑ์งบได้ชัวร์กว่าแบบเห็นๆ

*   **Django REST Framework (DRF)**
    *   **ทำไมถึงใช้ / ดีกว่าต้วอื่นยังไง:** ในขณะที่หลายทีมอาจจะใช้ Node.js หรือ Go แต่เราเลือก Django (Python) เพราะ "Time-to-Market" และ "Security" ระบบ ORM ของ Django แข็งแกร่งมาก ช่วยให้เราจัดการ Database Schema ที่ซับซ้อน (เช่น การทำ Follower, Room Ownership) ได้เร็ว และมีระบบ Authentication/Admin มาให้แบบพร้อมใช้
    *   **ข้อจำกัด:** ทำงานแบบ Synchronous (รอคิวประมวลผล) และกิน Memory มากกว่าภาษาอย่าง Go หากมีคนยิง API เข้ามาพร้อมกันหลักล้านคน อาจจะเจอปัญหาคอขวด (แต่เสกลของเราปัจจุบันยังรับได้สบาย)
*   **Daphne (ASGI Server)**
    *   **ทำไมถึงใช้:** เนื่องจาก Django ปกติเก่งแค่ HTTP Request (ไป-กลับ) แต่แอปเราต้องมี **WebSockets** (เชื่อมต่อค้างไว้) เพื่อทำแบบ Real-time เราจึงต้องมี Daphne มาครอบ Django อีกที เพื่อให้รองรับ Asynchronous I/O 
    *   **ตัวอย่างการใช้งาน:** ใช้ดัน Notification แบบ Real-time หรืออัปเดตสถานะว่า "A ยกมือขอพูดในห้อง" ส่งไปให้ทุกคนในห้องเห็นพร้อมกันโดยไม่ต้องกด Refresh
*   **Next.js (SSR)**
    *   **ทำไมถึงใช้:** การใช้ Next.js ให้ทำ SSR (Server-Side Rendering) บน VPS ของเราเอง ทำให้หน้า Admin สามารถคิวรี (Query) ข้อมูลสถิติหนักๆ ให้เสร็จบนเซิร์ฟเวอร์ก่อน แล้วค่อยพ่นเป็นหน้าเว็บเบาๆ ส่งมาให้บราวเซอร์แอดมิน (เร็วกว่าและปลอดภัยกว่าไปดึงจาก Client-side)

## 3. Media Cluster: WebRTC Engine (ระบบเสียงความหน่วงต่ำ)

นี่คือส่วนที่แพงที่สุดและท้าทายที่สุดของโครงสร้างทั้งหมด เราใช้ **LiveKit (Selective Forwarding Unit - SFU)**

*   **ทำไมไม่ใช้ P2P (Peer-to-Peer):** ถ้าใช้ WebRTC แบบดั้งเดิม (Mesh/P2P) มือถือคนพูด 1 คน ต้องอัปโหลดเสียงส่งให้คนฟัง 100 คนในห้องพร้อมกัน (Bandwidth มือถือพังพินาศ) แบบ **SFU ของ LiveKit** คนพูดจะส่งเสียงขึ้น Server แค่ 1 เส้น แล้ว Server จะ "คัดลอกและกระจาย" เสียงนั้นไปให้คนฟังทั้ง 100 คนเอง (ลดภาระมือถือผู้ใช้)
*   **ทำไมถึงใช้ LiveKit / ตัวอย่างการใช้งาน:** ตลาดแอปเสียงยุคใหม่ (รวมถึง OpenAI Realtime API) ล้วนใช้ LiveKit เพราะ Scale ง่ายและมี SDK สำหรับ Flutter/Python ครบถ้วน รวมถึงมีระบบ Signaling (จองคิวพูด) และระบบ Data Channel (ส่งข้อความแชทในห้อง) มาให้พร้อมในตัว
*   **การแบ่ง Protocol ที่สำคัญ:**
    *   **Signaling (พอร์ต 7880 แบบ TCP/WS):** ทำหน้าที่เหมือน "ฝ่ายธุรการ" เอาคีย์เข้าไปยืนยันตัวตน ขออนุญาตเข้าห้อง
    *   **Media Session (พอร์ต 7882 แบบ UDP):** เป็นท่อส่งเสียงเข้าห้อง *ทำไมต้อง UDP?* เพราะเสียงต้องการความ Real-time สูง หากสัญญาณอินเทอร์เน็ตสะดุด UDP จะข้ามเฟรมที่หายไปเลย (เสียงอาจจะกลืนนิดนึงแต่ไม่ดีเลย์) ต่างจาก TCP ที่จะหยุดรอโหลดข้อมูลที่หายไปจนครบ ทำให้คนพูดคุยกันละสายดีเลย์ (Out of sync)
*   **ข้อจำกัด:** บริโภค CPU และ Bandwidth ของเซิร์ฟเวอร์มหาศาล หากห้องมีคนฟังเกินหลักพันคน VPS เครื่องเดียวอาจจะเอาไม่อยู่ ต้องทำ Cloud Scaling หรือใช้ LiveKit Cloud แทน

## 4. Data Storage & Workers (การจัดการข้อมูลและงานเบื้องหลัง)

*   **PostgreSQL (ฐานข้อมูลหลัก)**
    *   **ทำไมถึงใช้:** แอปของเราเน้นความสัมพันธ์ของข้อมูล (Relational Data) เช่น User A Follow User B และ User B เป็นเจ้าของ Room C การใช้ SQL Database แบบ Postgres ยืนยันความสมบูรณ์ของข้อมูล (ACID Compliance) ได้ดีกว่า NoSQL (อย่าง MongoDB) ข้อมูลเงิน ข้อมูล Profile จะไม่มีทางสูญหายหรือเกิด State ไม่ตรงกัน
    *   **ข้อจำกัด:** การสเกลในแนวนอน (Horizontal Scaling) ทำได้ยากกว่า NoSQL
*   **Redis (In-Memory Data Store)**
    *   **ทำไมถึงใช้ / ตัวอย่าง:** Redis ทำงานบนแรม (RAM) จึงเร็วระดับ Microsecond เราเอามาเป็น **Swiss Army Knife (มีดพับสวิส)** ทำ 2 หน้าที่หลักคือ:
        1.  **Channel Layer (Pub/Sub):** ห้องแชทมีคนร้อยคน เมื่อมีคนกดไลก์ Django จะโยนคำสั่งลง Redis แล้ว Redis จะกระจาย (Broadcast) แจ้งเตือนผ่าน Daphne ออกไปหา 100 คนพร้อมกันในเสี้ยววินาที
        2.  **Task Queue:** ใช้เป็นกระดานแปะโพสต์อิท เพื่อสั่งงานบอท
    *   **ข้อจำกัด:** ข้อมูลอยู่บน RAM ถ้าเซิร์ฟเวอร์ดับ (ไฟตก) ข้อมูลที่ค้างในระบบคิวอาจจะหายได้ (แต่เราเซฟข้อมูลถาวรใน Postgres อยู่แล้ว)
*   **Python Music/Testing Bot Worker**
    *   **ทำไมถึงใช้:** งานสตรีมเสียงเพลง หรือบอททดสอบระบบ เป็นงานที่ต้อง "เปิดการเชื่อมต่อค้างไว้หลายชั่วโมง" (Long-running process) เราเอาไปผูกกับ Django API ปกติไม่ได้ (เพราะจะทำ API ค้างและ Timeout) จึงต้องแยกโปรแกรม Worker ออกมาต่างหาก คอยอ่านงานโง่ๆ จาก Redis Queue แล้วรันตัวมันเองเชื่อมต่อเข้า LiveKit ไปเงียบๆ เบื้องหลัง

## 📡 สรุป Port Mapping & Data Flow (เจาะลึกทิศทางการไหลของข้อมูล)

เพื่อให้ผู้ฟังหรือวิศวกรเห็นภาพชัดเจนว่า ระบบคุยอะไร ไปหาใคร และวิ่งผ่านช่องทางไหน (เปิดอกคุยเรื่อง Network Security):

| Service | Port / Protocol | Exposure | ใครคุยกับใคร (Data Flow) และคุยเรื่องอะไร? (Example) |
| :--- | :--- | :--- | :--- |
| **Caddy Gateway** | 80 & 443 (TCP) | **Public** | **โลกภายนอก ➡️ หน้าด่าน (HTTPS เสมอ):**<br>- แอบมือถือผู้ใช้ (Flutter) ยิงขอ Login Payload (`/api/login`)<br>- ผู้ใช้กดจอยหน้าแอป คุย WebSocket ผ่าน wss://โดเมนเรา/ws/ |
| **Django API / Daphne** | 8000 (TCP) | Internal | **Caddy ➡️ Backend:**<br>- *ไป-กลับ:* ถ้ายิง API มา Caddy จะมุดท่อส่งเข้าพอร์ต 8000 ของคอนเทนเนอร์นี้ เพื่อไปเช็ค User Password ในฐานข้อมูลแล้วตอบกลับ<br>- *ค้างสาย:* ถ้าเป็น WebSocket ก็ค้างสายไว้คุย Notification ยาวๆ |
| **Next.js Dashboard** | 3000 (TCP) | Internal | **Caddy ➡️ Admin UI:**<br>- แอดมินล็อกอินดู Dashboard ระบบ Caddy จะส่ง Traffic มุดมาที่พอร์ต 3000 เพื่อ Render หน้าสถิติ HTML ส่งกลับไปโชว์บราวเซอร์ |
| **LiveKit API (Signaling)** | 7880 (TCP / WS) | **Public** | **Flutter / Bot Worker ➡️ LiveKit (ต่อตรง ไม่ผ่าน Caddy):**<br>- ผู้เล่นเอา Token ไปเคาะประตู LiveKit (พอร์ตนี้หน้าที่คือ "เช็คตั๋วข้ามแดนและส่งคำสั่ง")<br>- ตัวอย่างข้อมูล: "นาย A ขอกดเปิดไมค์", "คนในห้อง B มี 5 คนนะ", "นาย C ขอยกมือ" (เป็นแค่ข้อมูลสถานะห้อง ไม่ใช่เสียง!) |
| **LiveKit RTC (Media Plane)** | 7881-7882 (**UDP** / TCP) | **Public** | **Flutter / Bot Worker ➡️ LiveKit (ต่อตรง ไม่ผ่าน Caddy):**<br>- นี่คือพระเอกของสถาปัตยกรรม **"ท่อลำเลียงเสียงเพียวๆ เดือดๆ"**<br>- 🗣️ ขณะที่คนกำลังพูด ตัวแอปมือถือจะแพ็กเอาคลื่นเสียง **ยิงรัวๆ อย่างบ้าคลั่งผ่านโพรโทคอล UDP (พอร์ต 7882)** ขึ้นไป เพื่อให้เซิร์ฟเวอร์กระจายเสียงนั้นลงมาให้คนฟังร้อยกว่าคนพร้อมๆ กัน! (ถ้าใช้ TCP หรือมุดผ่าน Proxy ตรงนี้จะทำเสียงช้าจนฟังไม่รู้เรื่อง) |
| **PostgreSQL** | 5432 (TCP) | Private | **Django ➡️ Database:**<br>- โดนปิดตายจากหน้า Internet โดยเด็ดขาด<br>- คุยเฉพาะในวง Docker เผื่อดึงข้อมูล User ว่าชื่ออะไร ใคร Block ใครไว้บ้าง |
| **Redis** | 6379 (TCP) | Private | **Django ↔ Daphne ↔ Bot Worker:**<br>- ทำงานเงียบๆ อยู่หลังบ้านคอยรับส่งข้อความ<br>- Django จับยัดข้อความสั่งให้ Bot Worker เล่นเพลงลงคิว Redis -> Bot Worker เห็นปุ๊บวิ่งไปเอา Token แล้วเสียบ LiveKit (7880, 7882) เอง |

## 5. การแก้แง่มุมความเป็นส่วนตัว (Privacy Logic vs Clubhouse)

**ปัญหาของ Clubhouse:** 
ผู้ใช้มักจะถูกเปิดเผยตัวตน (Real Identity) เพราะระบบนำเบอร์โทรศัพท์ไป Sync กับสมุดผู้ติดต่อ (Contact Book) ใครกดเข้าห้องหัวข้อสุ่มเสี่ยง เช่น ซึมเศร้า ปัญหาครอบครัว เพื่อนในชีวิตจริงจะได้รับการแจ้งเตือน (Push Notification) ทำให้เกิด Social Anxiety

**วิธีที่แอปเรา (VivaClub) ใช้แก้ปัญหาผ่าน System Architecture:**

1.  **Dual Identity System (ระบบตัวตนคู่ขนาน)**
    *   **ใน Database:** บัญชีผู้ใช้ (User Account) ถูกแยกส่วนข้อมูลจริง (อีเมล/เบอร์โทรศัพท์) ออกจากข้อมูลในห้องสนทนาโดยสิ้นเชิง
    *   **ในแอปพลิเคชัน:** ผู้ใช้จะถูกบังคับให้ใช้ **"Ghost Profile"** (ข้อมูลตัวตนสมมติ เช่น `ghost_id`, Avatar แบบสุ่ม และชื่อเล่นชั่วคราว) ในการทำกิจกรรมทุกอย่างในชุมชน
2.  **LiveKit Token & Metadata Sanitization (การสกัดข้อมูลก่อนสตรีมเสียง)**
    *   ตอนที่ User กดเข้าห้อง Backend ของเราจะทำการสร้าง JWT Token เพื่อไปคุยกับ LiveKit ซิร์ฟเวอร์ 
    *   **Logic สำคัญคือ:** แทนที่เราจะยัด `user_id` จริงลงไปใน Token เราทำการสกัดเอาเฉพาะ `ghost_id` และข้อมูลอวตารสมมติ ยัดใส่ลงไปใน **LiveKit Metadata** แทน 
    *   **ผลลัพธ์:** แม้จะมี Hacker ดักจับ Packet ในแอป หรือมีคนพยายามแกะข้อมูล API เขาจะเห็นแค่ว่า "Ghost_123" กำลังพูดอยู่ โดยไม่มีทางโยงกลับไปอ้างอิงถึง Email/เบอร์โทร หรือ User จริงใน Database ได้เลย
3.  **Zero Contact Sync & Anonymous Follow Graph**
    *   ระบบการทำ Follower/Following ของเรา ผูกโยงกับตาราง `ghost_profile` ไม่ได้ไปแตะต้องรายชื่อเบอร์โทรศัพท์ในเครื่อง 
    *   ถ้าผู้ใช้กด Follow ใคร ระบบจะจำแค่ว่า "Ghost A ตาม Ghost B" ไม่มีการส่ง Push notification แจ้งเตือนเพื่อนในชีวิตจริงให้ตกใจ

## 6. การบริหารจัดการผู้ใช้งานกลุ่มเสี่ยงสูง (Severe Critical / SOS Routing)

**ปัญหา:** ผู้ใช้งานที่มีความเสี่ยงสูง (Severe Critical) เช่น มีภาวะซึมเศร้ารุนแรง มักจะต้องรอคิวในระบบนานเกินไป ซึ่งในทางการแพทย์ถือเป็นช่วงเวลาหน้าสิ่วหน้าขวาน (Golden Minute)

**การทำงานและ System Logic (VivaClub SOS System):**

1.  **Automated PHQ-9 Assessment (คัดกรองอัตโนมัติ):**
    *   ระบบจะให้ผู้ใช้งานทำแบบประเมิน **PHQ-9 (แบบคัดกรองโรคซึมเศร้า 9 คำถาม)** 
    *   หาก Algorithm คำนวณคะแนนได้ **มากกว่า 19 คะแนน** (เกณฑ์ความเสี่ยงรุนแรง) แอปพลิเคชัน (Frontend) จะทำการ **ปลดล็อกปุ่มพิเศษ "SOS Call"** ขึ้นมาให้แทรกไปยังหน้าแรกทันที
2.  **Priority Queue System (ระบบลัดคิวฉุกเฉิน):**
    *   เมื่อผู้ใช้กด SOS Call คำขอนั้นจะถูกส่งเข้า **Priority Queue (คิวพิเศษ)** ในระบบ Backend 
    *   ระบบคำนวณคิว (Matchmaking) จะให้ Priority งานนี้สูงสุด ลัดคิวผู้ใช้งานทั่วไป และดึงสายลัดให้คุยกับ **"แพทย์ที่กำลังเข้าเวร (Standby Doctor)"** ทันที เพื่อประเมินอาการ ปฐมพยาบาลจิตใจ (Psychological First Aid) และหาทางออกฉุกเฉินร่วมกันภายในกรอบเวลา **15 นาที**
3.  **Anti-Spam & State Management (การป้องกันการก่อกวน):**
    *   **Default Limit:** เพื่อป้องกันการก่อกวน หรือคนปกติกดสแปมเพื่อแทรกคิว ระบบ Database จะจำกัดสิทธิ์การกด SOS Call ไว้ที่ **1 ครั้ง/เดือน**
    *   **Doctor Override (Manual Escalation):** แต่ในกรณีที่แพทย์ประหยัดสายเสร็จแล้ว ประเมินว่าเคสนี้ **"มีความน่าเป็นห่วงจริง หน้าสิ่วหน้าขวาน"** แพทย์สามารถกดปรับ State ในระบบเพื่อคืนสิทธิ์กลับมา ทำให้ผู้ใช้คนนี้สามารถใช้ SOS Call ได้เรื่อยๆ จนกว่าทีมแพทย์เฉพาะทางจะประเมินอีกครั้งและลงมติ **"ลดสถานะ (Downgrade) เป็นเพียงการเฝ้าระวัง"** สิทธิ์จึงจะถูกลดกลับเป็น 1 ครั้ง/เดือนตามเดิม

## 7. การจัดการพฤติกรรมก่อกวน (Troll/Spam Management & Community Moderation)

**ปัญหา:** เนื่องจากแอปพลิเคชันใช้ระบบ "Ghost Profile" (ตัวตนสมมติ) จึงเลี่ยงไม่ได้ที่จะมีผู้ใช้บางกลุ่มสร้างบัญชีผีเพื่อมาป่วนห้องเสียงโดยเฉพาะ (เช่น เปิดไมค์ส่งเสียงดังด่าทอ แล้วปิดไมค์หนี) การรอให้ Admin กลางมาจัดการจะไม่ทันท่วงที

**การทำงานและ System Logic (Self-Regulated Community):**

1.  **User Trust Score (ระบบคะแนนกรรม / Karma):**
    *   ผู้เล่นทุกคนจะมีคะแนนความน่าเชื่อถือผูกกับ Ghost Profile 
    *   ระบบมีอัลกอริทึมให้รางวัลและบทลงโทษ: หากแกล้ง Report คนอื่นมั่วๆ กรรมจะตามสนองโดยการฝั่งตัวเองโดนหักคะแนน แต่หาก Report แล้วระบบตรวจสอบว่าคนนั้นทำผิดจริง (เช่น โดนโหวตเตะออก) ผู้ที่ Report จะได้คะแนนบวกเพิ่ม
2.  **Auto-Ban Threshold (ระบบเตะอัตโนมัติด้วยเสียงรังวัด):**
    *   เมื่อคนในห้องรู้สึกรำคาญและพร้อมใจกันโหวต Report ผู้ใช้ที่กำลังป่วน หากยอดโหวตผ่านเกณฑ์ที่ตั้งไว้ (Threshold) ระบบ Backend จะสั่งยิง **LiveKit Webhook (`MuteParticipant` หรือ `RemoveParticipant`)** อัตโนมัติ เพื่อเตะหรือปิดไมค์คนนั้นทันที โดยไม่ต้องง้อ Admin กลางให้เสียเวลา
3.  **Community Moderator (การตั้งผู้คุมกฎอาสาสมัคร):**
    *   ระบบมีกลไกตรวจสอบผู้เล่นน้ำดี (เช่น เช็คจากสถิติใช้งาน > 50 ชั่วโมง และมีคะแนน Trust Score > 180)
    *   ผู้เล่นเหล่านี้จะถูกเลื่อนขั้นเป็น **"Community Moderator"** ได้รับตราอาร์มพิเศษหน้า Profile และได้รับสิทธิพิเศษ (Privileges) ในการกดปุ่ม "เตะ (Kick) หรือ ปิดไมค์ (Mute)" ผู้ใช้ที่ก่อกวนออกจากห้องได้โดยตรง
    *   **Audit Logging Backend:** เพื่อป้องกันการลุแก่อำนาจ ทุกๆ Action ของ Moderator จะถูกบันทึกลง Database (Audit Log) อย่างละเอียด หาก Admin กลางตรวจสอบพบว่าใช้อำนาจเตะคนมั่วซั่ว ระบบสามารถปลด ยึดตราอาร์ม และแบนบัญชี Moderator นั้นทิ้งได้อย่างง่ายดาย

## 8. การคุ้มครองข้อมูลส่วนบุคคล (PDPA Compliance & Data Security)

**ปัญหา:** แอปพลิเคชันที่จัดการความเสี่ยงด้านสุขภาพจิตและข้อมูลผู้โทรศัพท์ จำเป็นต้องปฏิบัติตาม พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล (PDPA) อย่างเคร่งครัด หากข้อมูลรั่วไหลอาจเกิดผลกระทบต่อชีวิตผู้ใช้

**การทำงานและ System Logic ทางเทคนิค:**

1.  **Data Minimization (หลักการเก็บข้อมูลเท่าที่จำเป็น):**
    *   ตอนสมัครสมาชิก ระบบเราต้องการเพียงแค่ **Email หรือ เบอร์โทรศัพท์** เพื่อใช้ยืนยันตัวตน (Authentication) เท่านั้น 
    *   เราไม่ขอบัตรประชาชน ไม่ขอชื่อ-นามสกุลจริง ไม่ขอที่อยู่ (นอกจากในเคสวิกฤตที่ยินยอมให้แพทย์ติดต่อ) ทำให้ลดภาระในการเก็บรักษาข้อมูลที่มีความ Sensitive สูง 
2.  **Separate Identity Tables (การแยกเก็บข้อมูลแบบไซโล):**
    *   ใน PostgreSQL Database เรามี Table `auth_user` (เก็บ Email รหัสผ่านที่เข้ารหัสแล้ว) แยกขาดจากตาราง `ghost_profile` (เก็บเฉพาะ ID สมมติและรูปโปรไฟล์ผี)
    *   การประมวลผลทางสถิติ หรือการสตรีมมิ่ง จะดึงไปแค่ข้อมูลจาก `ghost_profile` เท่านั้น ทำให้ข้อมูลส่วนตัว (PII - Personally Identifiable Information) ปลอดภัยอยู่ใน Table ที่เข้าถึงได้โดย Superadmin เพียงผู้เดียว (Isolation)
3.  **Encrypted in Transit (การเข้ารหัสข้อมูลระหว่างทาง):**
    *   **HTTP/WebSocket:** ข้อมูลทุกอย่างที่วิ่งเข้า-ออกแอปผ่าน **Caddy Gateway** จะถูกบังคับให้วิ่งบน `HTTPS` และ `WSS` (WebSocket Secure) พร้อมเข้ารหัส SSL/TLS certificate อัตโนมัติ (ผ่าน Let's Encrypt)
    *   **Voice Data (เสียง):** การคุยเสียงทั้งหมดผ่าน LiveKit (WebRTC) จะถูกเข้ารหัสแบบ **SRTP (Secure Real-Time Transport Protocol)** และ **End-to-End Encryption (E2EE) Options** เป็นค่าเริ่มต้น ทำให้ไม่มีใคร (แม้แต่ ISP หรือผู้จัดหา VPS) สามารถแอบดักฟัง (Sniff) แพ็กเก็ตเสียงกลางทางได้
4.  **Right to be Forgotten (สิทธิในการถูกลืม):**
    *   เราออกแบบ API ให้รองรับ **"Soft Delete" และ "Hard Delete"**
    *   เมื่อผู้ใช้งานขอลบบัญชี ระบบจะตัดความสัมพันธ์ (Cascade Delete) ข้อมูลใน `ghost_profile`, เสียงอัด, และประวัติการคอมเมนต์ทิ้งทั้งหมดตามสิทธิ์ใน PDPA มาตรา 33 (Right to Erasure) ทันทีบนฐานข้อมูลหลัก

## 9. สถาปัตยกรรมระดับซอฟต์แวร์ (Software Architecture & State Management)

**โครงสร้างระดับแอปพลิเคชัน (Frontend - Flutter):**
เราออกแบบแอปพลิเคชันโดยยึดหลัก **Clean Architecture** แบ่งโครงสร้างโค้ดออกเป็น 3 เลเยอร์หลัก เพื่อให้โค้ดดูแลรักษาง่าย (Maintainable) และเขียนเทสต์ได้ง่าย (Testable):

1.  **Presentation Layer (UI & State):** ประกอบด้วยหน้าจอ (Screens/Widgets) ทาง UI และ BLoC/Cubit สำหรับจัดการ State
2.  **Domain Layer (Business Logic):** ตัวกำหนดโครงสร้างข้อมูล (Entities) และ Use Cases ต่างๆ (เช่น `JoinRoomUseCase`, `MuteMicrophoneUseCase`) เลเยอร์นี้จะไม่มีโค้ดที่ผูกกับ Flutter SDK เลย
3.  **Data Layer (API & Local Storage):** จัดการเรื่องการยิง HTTP Request ไป Backend (Django), การต่อ WebSocket, หรือการจัดการฐานข้อมูลในเครื่อง (SQLite / SharedPreferences)

**ทำไมถึงเลือกใช้ BLoC (Business Logic Component)?**
แอปพลิเคชันประเภท Live Audio Room มีความซับซ้อนเรื่อง **"สถานะ (State)"** สูงมาก การใช้ `setState()` ทั่วไปหรือ Provider อาจจะเอาไม่อยู่ BLoC จึงเข้ามาแก้ปัญหาเหล่านี้:

1.  **Separation of Concerns (การแยก UI ออกจาก Logic อย่างเด็ดขาด):**
    *   BLoC บังคับให้เรามองทุกอย่างเป็น **Event (สิ่งที่ User ทำ) -> State (ผลลัพธ์ที่ UI ต้องแสดง)**
    *   ตัวอย่าง: `MuteMicEvent` -> BLoC ประมวลผลคุยกับ LiveKit -> พ่น `RoomState(isMuted: true)` ออกมาให้ UI ทำปุ่มไมค์เป็นสีแดง
2.  **จัดการ Async & Stream Operations ได้ดีเยี่ยม:**
    *   แอปต้องรับข้อมูลแบบ Real-time (Stream) จาก **LiveKit WebRTC** ตลอดเวลา (เช่น ใครกำลังพูดอยู่ - Active Speakers, สถานะเน็ตเวิร์คหลุดเกิด Reconnecting) BLoC ทำงานบนพื้นฐานของ `Streams` จึงรองรับข้อมูลไหลเข้าออกแบบต่อเนื่องได้เสถียรมาก
3.  **Predictability (คาดเดาสถานะได้ 100%):**
    *   ทุกครั้งที่ห้อง Live มีการอัปเดต เช่น มีคนยกมือตามา (Hand Raised) หรือมีคนใหม่เดินเข้าห้อง BLoC จะพ่น State ใหม่ทับ State เดิมเสมอ ทำให้เรามั่นใจว่าถ้า State เป็นหน้าตาแบบนี้ UI ทุกจุดในแอป (เช่น ไอคอนยกมือ, รูปโปรไฟล์มุมจอ) จะต้องอัปเดตและแสดงผลตรงกันทั้งหมดโดยไม่มีบั๊ก UI ค้าง
4.  **ป้องกัน Race Conditions:**
    *   ในห้องเสียงคนอาจจะกดปุ่มแย่งไมค์พร้อมกัน หรือเน็ตกระตุก BLoC สามารถใช้ Event Transformers (เช่น `droppable`, `throttle`) เพื่อป้องกันไม่ให้แอปทำงานซ้ำซ้อนจนพังได้
