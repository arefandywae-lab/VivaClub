# บทที่ 9: ปัญหาที่พบและวิธีแก้ไข (Challenges and Solutions)
# Chapter 9: Challenges and Solutions

---

> บทนี้รวบรวมปัญหาทางวิศวกรรมสำคัญที่พบระหว่างการพัฒนา VivaClub ตั้งแต่ขั้นตอนการตั้งค่าเซิร์ฟเวอร์จนถึงการใช้งานจริง แต่ละปัญหาถูกบันทึกเพื่อเป็นบทเรียนทางวิศวกรรม: อาการ → สาเหตุ → การวิเคราะห์ → วิธีแก้ไข → ผลลัพธ์

## Challenge 1: Redis WebSocket Tuple Error
**อาการ:** ระบบ WebSocket ล้มเหลวทั้งหมด ทำให้ไม่สามารถรับการแจ้งเตือนหรือแชทได้ โดยระบบแจ้งข้อผิดพลาดเกี่ยวกับ 'tuple' object
**สาเหตุ:** ไลบรารี `channels_redis` เวอร์ชัน 4.x เปลี่ยนรูปแบบการรับค่า Host จากแบบ Tuple เป็นแบบ URL String
**วิธีแก้ไข:** ทำการปรับปรุงไฟล์การตั้งค่า (`settings.py`) โดยเปลี่ยนรูปแบบการระบุที่อยู่ของ Redis Server จากเดิมที่เป็นลิสต์ของ Tuple ให้กลายเป็น String URL ที่ระบุโปรโตคอลและพอร์ตอย่างชัดเจน (เช่น `redis://redis:6379`)
**ผลลัพธ์:** ระบบ WebSocket กลับมาทำงานได้ปกติ โดยมีความหน่วงในการส่งข้อมูลต่ำกว่า 200ms

## Challenge 2: Port Conflict — Apache2 vs Caddy
**อาการ:** เซิร์ฟเวอร์ Caddy ไม่สามารถทำงานได้และแจ้งข้อผิดพลาด "address already in use"
**สาเหตุ:** ระบบปฏิบัติการของ VPS (Ubuntu) มีการติดตั้งและรัน Apache2 ไว้เป็นค่าเริ่มต้น ซึ่งแย่งพอร์ต 80 และ 443 ไปใช้งานก่อน
**วิธีแก้ไข:** ทำการหยุดการทำงานของ Apache2 (Stop service) และยกเลิกการรันอัตโนมัติเมื่อเปิดเครื่อง (Disable service) จากนั้นจึงสั่งให้ Docker Compose เริ่มการทำงานของ Caddy ใหม่
**ผลลัพธ์:** Caddy สามารถทำงานและสร้างใบรับรอง HTTPS (Let's Encrypt) ได้โดยอัตโนมัติภายใน 2 นาที

## Challenge 3: Mismatch Environment Variable Names
**อาการ:** ระบบควบคุมห้องสนทนา (Invite/Mute/Kick) ใช้งานไม่ได้และแจ้งข้อผิดพลาด 401 หรือ 502
**สาเหตุ:** ชื่อตัวแปรในไฟล์ `.env` ไม่ตรงกับชื่อที่โค้ด Django เรียกใช้ ทำให้ระบบไปเชื่อมต่อกับเซิร์ฟเวอร์ LiveKit ตัวเก่าที่หมดอายุแล้ว
**วิธีแก้ไข:** ตรวจสอบและแก้ไขชื่อตัวแปรสภาพแวดล้อม (Environment Variables) ทั้งในไฟล์คอนฟิกของ Docker และในโค้ด Python ให้ตรงกัน 100% (เป็น `LIVEKIT_API_URL`)
**ผลลัพธ์:** ระบบควบคุมห้องสนทนาทำงานได้อย่างถูกต้องสมบูรณ์

---

## Challenge 4: Bot Audio Stutter (asyncio.sleep Drift)
**อาการ:** บอทเปิดเพลงมีเสียงกระตุกและหยุดชะงักเป็นระยะ ยิ่งเปิดนานยิ่งรุนแรงขึ้น
**สาเหตุ:** การใช้คำสั่ง `asyncio.sleep(0.010)` มีความคลาดเคลื่อนสะสม (Drift) ทำให้การส่งข้อมูลเสียงไม่สม่ำเสมอตามมาตรฐาน 10ms ของ WebRTC
**วิธีแก้ไข:** เปลี่ยนกลไกการหน่วงเวลาจากการรอแบบคงที่ เป็นการคำนวณเวลาที่ควรจะส่งเฟรมถัดไปเทียบกับจุดเริ่มต้น (Absolute Time Pacing) โดยใช้ `time.monotonic()` เป็นตัววัด เพื่อกำจัดค่าความคลาดเคลื่อนสะสมให้เป็นศูนย์
**ผลลัพธ์:** เสียงจากบอทมีความเสถียรและไหลลื่นตลอดการทดสอบ โดยมีค่าความคลาดเคลื่อนต่ำกว่า 1ms ต่อชั่วโมง

## Challenge 5: Listener Count Double-Counting
**อาการ:** จำนวนผู้ฟังในห้องสนทนาแสดงผลผิดพลาด (มากกว่าความเป็นจริง 2 เท่า)
**สาเหตุ:** ระบบมีการนับจำนวนผู้เข้าร่วมซ้ำซ้อน ทั้งจาก API ของแอปพลิเคชัน และจาก Webhook ของ LiveKit
**วิธีแก้ไข:** ตัดตรรกะการเพิ่มจำนวนผู้ใช้ในฝั่ง API ออก และกำหนดให้ Webhook จากเซิร์ฟเวอร์สื่อเป็น "แหล่งข้อมูลความจริงเดียว" (Single Source of Truth) พร้อมทั้งใช้คำสั่ง `F()` expression ในระดับฐานข้อมูลเพื่อป้องกันปัญหาการเขียนข้อมูลทับกัน (Race Condition)
**ผลลัพธ์:** จำนวนผู้ฟังแสดงผลได้อย่างแม่นยำ 100% ตามจำนวนผู้ใช้งานจริง

---

## Challenge 6: Ghost Profile Follow Broken
**อาการ:** กดติดตาม (Follow) ผู้ใช้ในห้องสนทนาแล้วข้อมูลไม่ถูกบันทึก
**สาเหตุ:** แอปพลิเคชันส่ง User ID ไปให้ API แต่ API ต้องการ Ghost ID ในการบันทึกการติดตาม
**วิธีแก้ไข:** ปรับปรุงระบบการส่งข้อมูลในห้องสนทนา โดยฝั่งเซิร์ฟเวอร์จะฝัง Ghost ID ไว้ในข้อมูล Metadata ของผู้เข้าร่วมทุกคน และฝั่งแอปพลิเคชันจะดึง ID นี้มาใช้ในการเรียก Follow API แทน
**ผลลัพธ์:** ระบบการติดตามทำงานได้อย่างถูกต้องและแสดงผลทันทีหลังกดปุ่ม

---

## Challenge 7: Thai Carrier MTU Blackhole
**อาการ:** ผู้ใช้เครือข่ายมือถือในไทย (AIS, True, DTAC) เชื่อมต่อห้องสนทนาได้แต่ไม่ได้ยินเสียง
**สาเหตุ:** เครือข่ายมือถือมีการปิดกั้นข้อมูล UDP ขนาดใหญ่ (Path MTU Blackhole) ซึ่งเป็นโปรโตคอลหลักของ WebRTC
**วิธีแก้ไข:** ติดตั้งและคอนฟิก TURN Server ให้รองรับการส่งข้อมูลผ่านโปรโตคอล TCP พอร์ต 443 เพื่อหลีกเลี่ยงข้อจำกัดของเครือข่ายมือถือและกำแพงไฟวอลล์
**ผลลัพธ์:** ผู้ใช้ทุกเครือข่ายสามารถใช้งานระบบเสียงได้ตามปกติ แม้อยู่บนเครือข่ายมือถือ 4G/5G

---

## Challenge 8: 401 Unauthorized on Public Endpoints
**อาการ:** ผู้ใช้ใหม่ไม่สามารถสมัครสมาชิกหรือเข้าสู่ระบบได้ (แจ้ง Unauthorized)
**สาเหตุ:** การตั้งค่าสิทธิ์การเข้าถึงแบบ Global กำหนดให้ทุก API ต้องมีรหัสผ่าน (Token) ก่อนเข้าถึง รวมถึงหน้าสมัครสมาชิกเองด้วย
**วิธีแก้ไข:** กำหนดข้อยกเว้นสิทธิ์ (Permission Override) ให้กับหน้าลงทะเบียนและเข้าสู่ระบบเป็นแบบ `AllowAny` เพื่อให้ผู้ใช้ใหม่สามารถเข้าถึงได้โดยยังไม่ต้องมี Token
**ผลลัพธ์:** ระบบการลงทะเบียนและเข้าสู่ระบบกลับมาใช้งานได้ตามปกติ

---

## Challenge 9: LiveKit SDK Incompatibility
**อาการ:** ระบบควบคุมสมาชิกในห้องสนทนาแจ้งข้อผิดพลาด 500 หลังอัปเดตไลบรารี
**สาเหตุ:** ไลบรารี LiveKit Python SDK มีการเปลี่ยนแปลงครั้งใหญ่ (Breaking Change) จากระบบ REST API ไปเป็นโปรโตคอล Twirp RPC
**วิธีแก้ไข:** ทำการเขียนโค้ดในส่วนการสื่อสารกับ LiveKit ใหม่ทั้งหมด โดยเปลี่ยนจากการส่งค่าพารามิเตอร์แบบเดิมมาเป็นการใช้ Request Object ตามมาตรฐานใหม่ของ SDK
**ผลลัพธ์:** ระบบควบคุมห้องสนทนากลับมาทำงานได้ปกติและมีความเสถียรมากขึ้น

---

## Challenge 10: SOS Patient Screen Never Advances
**อาการ:** เมื่อคุณหมอกดรับสาย SOS แล้ว หน้าจอของคนไข้ยังคงค้างอยู่ที่ "รอคิว..." ไม่ยอมเข้าสู่โหมดวิดีโอคอล
**สาเหตุ:** หน้าจอแอปพลิเคชันฝั่งคนไข้ไม่มีระบบตรวจสอบสถานะการรับสายจากเซิร์ฟเวอร์หลังจากส่งคำขอไปแล้ว
**วิธีแก้ไข:** เพิ่มระบบตรวจสอบสถานะอัตโนมัติ (Polling Mechanism) โดยให้แอปพลิเคชันเรียกสอบถามสถานะ SOS ทุกๆ 5 วินาที หากพบว่ามีการรับสายแล้ว ระบบจะทำการเชื่อมต่อวิดีโอคอลทันที
**ผลลัพธ์:** คนไข้สามารถเข้าสู่การพูดคุยกับคุณหมอได้ภายในเวลาไม่เกิน 5 วินาทีหลังจากมีการรับสาย
